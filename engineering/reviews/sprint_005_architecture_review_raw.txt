# Governance assessment

Sprint 005 should not proceed directly to CT-001, the Compliance Test Catalog, or the Evaluation Report Template.

The compliant next step is to create the Sprint 005 Implementation Plan, complete architecture review and approval, and establish the approved plan as the Sprint 005 Execution Contract before creating further governance assets.

## 1. Governance compliance

The next step is:

```text
Sprint 005 Implementation Plan
        ↓
Change classification and TIA determination
        ↓
Architecture review and formal approval
        ↓
Approved Execution Contract
```

Only then should implementation begin.

The Engineering Contributor Guide requires every engineering modification to progress through planning, triage, approval, implementation, verification, and retrospective. It specifically says to create an Implementation Plan and that development begins only after approval by the architecture owner ([engineering_contributor_guide.md](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/governance/engineering_contributor_guide.md:60)).

The existing Sprint 005 document cannot substitute for this because:

- It is an architecture proposal, not an implementation plan.
- Its status remains `Proposed` ([sprint_005_architecture_proposal.md](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/sprints/sprint_005_architecture_proposal.md:4)).
- It does not constitute recorded approval.
- It does not provide the complete execution controls required by the Implementation Plan template.

## 2. Workflow consistency

Yes. Beginning implementation immediately would violate the repository workflow.

It would bypass:

1. **Planning** — creation of an Implementation Plan.
2. **Triage** — Class A/Class B classification and any required Testing Impact Analysis.
3. **Approval** — review and approval by the architecture owner.
4. **Approved-plan control** — implementation must follow the approved plan, with deviations requiring re-approval.

These rules are explicit in the Contributor Guide ([lines 62–68](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/governance/engineering_contributor_guide.md:62)) and its “Obedience to Approved Plans” rule ([line 88](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/governance/engineering_contributor_guide.md:88)).

The governing rule is not limited to runtime code. It applies to “engineering modifications.” Creating new governance files is a repository modification.

## 3. Implementation Plan requirement

Yes, Sprint 005 requires an Implementation Plan.

It is required by:

- The Engineering Contributor Guide’s Planning stage.
- The Engineering Change Governance Policy’s classification and TIA process.
- The repository’s Implementation Plan/Execution Contract template.
- The Governance Architecture, which places Implementation Plans and Execution Contracts in the Engineering Execution layer ([governance_architecture.md](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/governance/governance_architecture.md:203)).
- The README workflow, which identifies the Implementation Plan as the document reviewed and approved into an Execution Contract ([README.md](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/README.md:91)).

Its engineering purpose is to define:

- Files to create and modify.
- Task boundaries and dependencies.
- Change classification.
- TIA where applicable.
- Validation and acceptance criteria.
- Risks and rollback.
- Documentation synchronization.
- The authorized scope against which implementation can later be verified.

The Sprint 005 architecture proposal supplies architectural intent and proposed deliverables. It does not supply all these execution controls.

## 4. Approval requirement

Yes. Formal approval is required before implementation.

The expected approver is the **architecture owner**, as explicitly identified by the Contributor Guide.

Approval should cover:

- The Sprint 005 architecture proposal, which remains `Proposed`.
- The Implementation Plan and repository impact.
- The proposed file structure and deliverables.
- Change classifications and TIA conclusions.
- Validation and acceptance criteria.
- Risks, rollback, and permitted scope.
- Any findings from architecture review.

Approval matters because it creates an authoritative boundary between proposed work and authorized work. Without recorded approval, implementation has no governance evidence that its scope, architecture, and validation obligations were accepted.

## 5. Execution Contract requirement

Yes. After approval, Sprint 005 must have an Execution Contract.

The repository currently treats the approved Implementation Plan as the Execution Contract rather than necessarily requiring two independently authored documents. The template is explicitly titled “Implementation Plan / Execution Contract” ([implementation_plan_template.md](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/templates/implementation_plan_template.md:1)), and the README says the Implementation Plan is reviewed and approved as the Execution Contract.

Therefore, the compliant lifecycle can be:

```text
Draft Implementation Plan
        ↓ approval
Approved Implementation Plan / Execution Contract
```

A separate post-approval file is optional unless repository policy is amended to demand one. What is mandatory is an identifiable, approved contractual artifact.

It should contain:

- Approval metadata and date.
- Authorized scope.
- Files to create or modify.
- Task decomposition and dependencies.
- Change classification and TIA results.
- Validation and acceptance criteria.
- Risks and rollback.
- Documentation synchronization requirements.
- Stop-and-reapprove rules for deviations.

Governance assets are implementation for workflow purposes. “No runtime implementation” does not mean “no implementation.” Creating the catalog, templates, and CT-001 is implementation of the governance architecture.

## 6. Governance self-validation

Sprint 005 should become the first direct self-validation case.

RGV states that the workflow—not the feature—is the subject under validation and expects planning, classification, TIA, approval, implementation, verification, synchronization, and retrospective ([repository_governance_validation.md](/home/lskuo/googledrive/GitHub%20Project/SciForge-Edu/docs/governance/repository_governance_validation.md:210)).

Skipping the plan, approval, or execution contract would weaken RGV because the repository would be:

- Defining workflow conformance while not following that workflow.
- Producing compliance tests through an uncontrolled process.
- Claiming reproducibility without preserving authoritative execution evidence.
- Demonstrating that governance work is implicitly exempt from governance.
- Undermining GP-006 Governance Conformance in RGAM.

This would be a direct failure of governance “dogfooding.”

## 7. Risks of skipping governance gates

Skipping the Implementation Plan introduces:

- Undefined repository impact.
- Unrecorded change classifications.
- Missing TIA decisions.
- Ambiguous file ownership and artifact responsibilities.
- Incomplete acceptance and validation criteria.
- No controlled baseline for verification.

Skipping approval introduces:

- Implementation of an architecture that remains formally proposed.
- No evidence that the architecture owner accepted the scope.
- Conflicting interpretations of artifact authority.
- Uncontrolled architectural drift.
- Weak auditability and accountability.

Skipping the Execution Contract introduces:

- No authoritative implementation boundary.
- No enforceable stop-and-reapprove mechanism.
- No basis for determining whether implementation conformed.
- Scope creep and undocumented deviations.
- Reduced reproducibility for independent contributors.
- Weak evidence for later RGV evaluation.

Collectively, these omissions would make any later “workflow conformance” test partially self-contradictory.

## 8. Recommended sequence

```text
Existing Sprint 005 Architecture Proposal
        ↓
Architecture consistency review
        ↓
Sprint 005 Implementation Plan
        ↓
Change classification and TIA determination
        ↓
Formal architecture-owner approval
        ↓
Approved Implementation Plan becomes Execution Contract
        ↓
Compliance Test Catalog and template implementation
        ↓
CT-001 and Evaluation Report Template implementation
        ↓
Verification against the approved contract
        ↓
Documentation synchronization
        ↓
Sprint 005 retrospective
```

Architecture review should precede final approval because the proposal is still marked `Proposed`. The Implementation Plan may be drafted during that review, but implementation cannot begin until both architectural disposition and execution authorization are recorded.

## 9. Overall assessment

Proceeding directly to CT-001 and the Compliance Test Catalog would be governance non-compliance.

The assets are correctly identified as Sprint 005 deliverables, but identification in a proposed architecture document is not implementation authorization. The repository requires planning, triage, approval, and implementation under an approved plan/Execution Contract.

The only compliant next action is planning and approval—not governance asset creation.
