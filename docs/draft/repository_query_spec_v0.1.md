# Purpose

Define repository query semantics and search workflow for SciForge-Edu.

This specification focuses on:

- question retrieval
- filtering workflow
- repository indexing direction
- future query scalability

This document does not define implementation details.


# Design Philosophy

Repository search is not only file lookup.

The repository should support:

- curriculum-oriented retrieval
- assessment-oriented filtering
- usage-aware workflows
- future semantic search expansion

Search behavior should remain:

- deterministic
- inspectable
- explainable


# Search Goals

Primary goals:

- fast question retrieval
- reusable question bank workflow
- curriculum-aware filtering
- difficulty-aware filtering
- provenance-aware filtering
- future recommendation support

Secondary goals:

- semantic search
- AI-assisted retrieval
- usage analytics


# Query Categories


## Structural Queries

Structural queries operate on intrinsic Question properties.

Examples:

- uuid
- label
- question_type
- chapter
- tags
- subject

Typical usage:

- find all multiple-choice questions
- find Newton's Second Law questions
- find electrochemistry questions


## Statistical Queries

Statistical queries operate on observed assessment results.

Examples:

- correct_rate
- difficulty_index
- discrimination_index
- sample_size

Typical usage:

- find difficult questions
- find high-discrimination questions
- find unstable statistics


## Provenance Queries

Provenance queries operate on content origin metadata.

Examples:

- source_name
- source_type
- created_by
- model_version

Typical usage:

- find AI-generated questions
- find textbook-derived questions
- find manually verified questions


## Usage Queries

Usage queries operate on repository usage history.

Examples:

- recently used
- frequently selected
- never used
- archived

Typical usage:

- avoid repeated exam content
- recommend underused questions
- identify high-frequency questions


# Query Examples

Example search requests:

- "Find Newton's Second Law questions"
- "Find easy electrochemistry questions"
- "Find high-discrimination questions"
- "Find questions with misconception tags"
- "Find questions never used in exams"
- "Find questions generated by GPT-5"
- "Find recently modified questions"


# Repository Architecture Considerations


## Current Repository Structure

Current implementation:

- filesystem repository
- JSON-based storage
- repository index file
- Question-centered persistence


## Current Repository Constraints

Current limitations:

- linear search behavior
- limited indexing
- limited filtering support
- no ranking system


## Future Search Directions

Possible future directions:

- sqlite indexing
- hybrid repository index
- semantic embedding search
- ranking-based retrieval
- recommendation engine
- curriculum graph search


# Query System Principles

Repository search should prioritize:

- deterministic filtering
- reproducible results
- explicit metadata usage
- inspectable ranking logic

Repository search should avoid:

- opaque scoring behavior
- hidden filtering logic
- non-reproducible ordering


# Relationship with Question Model

Search categories should remain conceptually separated from Question intrinsic properties.

Examples:

- statistics are observed metadata
- usage history is external workflow metadata
- provenance represents content origin metadata

Question remains the primary domain object.


# Relationship with Snapshot System

Repository query structures may later appear in:

- api_snapshot.md
- repository architecture snapshots
- AI collaboration metadata

Search architecture should remain AI-readable.


# Open Questions

Current unresolved questions:

- should repository indexing remain filesystem-based?
- should statistics remain embedded in Question?
- should semantic search remain optional?
- should repository search support weighted ranking?
- should usage history become a separate model?
